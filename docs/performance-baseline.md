# Windows 性能与正确性基线（2026-10-01）

本轮使用同一台 Intel Core i7-13650HX、约 32 GB 内存的 Windows 11 22631 机器，Node 24.19.0、Milkdown 7.22.1。修改前取提交 `8a5416b493c8ad9306570e0c2fb940b7ea8e380f` 的实际源码，修改后取当前工作区；同一套依赖、数据及测量程序，各热缓存场景 30 次。原始结果见 [JSON](performance-baseline.json)。

## 测量范围

- 编辑和图片：隔离 Chromium 中运行真实 `Editor`/Crepe 和图片工具栏；编辑回调仅比较主流程原有的两次全文序列化与文本复用，未包含大纲、统计刷新或 Rust IPC。输入到回调包含 Milkdown 的 200 ms 防抖。
- 恢复和慢速保存：从实际 `main.ts` 提取函数，使用真实 `TabBar`，读取响应为预备文本/图片，保存响应可人为延迟；不将其耗时当作文件系统或整机启动耗时。
- 搜索：取实际 Rust 目录遍历源码，以同样 `rustc -O` 构建运行。仅加入目录/条目计数，不改遍历规则；首次调用单列，不宣称清空了系统缓存。
- 浏览器内存为每组样本抽取的 JS 堆峰值，前后在同一页面顺序运行，受到 GC、模块驻留和测试顺序影响；不能据此声称应用驻留内存改善。Rust 内存是独立进程的工作集。
- 这些是组件和后端基线，Windows WebView2 实机交互结果另见 [开发说明](development.md)。

## 本轮发现并修复

2026-10-02 追加目录可见性检查：真实 WorkspaceSidebar 组件配合模拟 IPC/visibilitychange，可见期间发生 1 次定时目录读取，隐藏 5.5 秒期间新增 0 次，恢复后立即新增 1 次。计数见 JSON 的 `directoryVisibilityRegression`。该组件检查不等同于 Windows 原生最小化回归。

标题 ID 的非历史追加事务会替换 ProseMirror 文档对象。原先按对象身份过滤回调会误丢有效标题编辑；现在用文档归属代次判断，允许同一文档的派生事务，阻止切换文档和重建编辑器后的旧回调。真实编辑器的标题编辑、快速换文档、重建三项回归通过。

## 复现

```powershell
node scripts/prepare-performance-benchmark.mjs performance
pnpm dev --host 127.0.0.1
# 浏览器打开 /output/tmp/performance/index.html 并点击 Run benchmark
node scripts/prepare-performance-benchmark.mjs performance-regressions regressions
# 浏览器打开其 index.html，点击 Run regressions
node scripts/prepare-search-benchmark.mjs
rustc --edition 2021 -O output/tmp/search-performance/benchmark.rs -o output/tmp/search-performance/benchmark.exe
output/tmp/search-performance/benchmark.exe output/tmp/search-performance before
output/tmp/search-performance/benchmark.exe output/tmp/search-performance after
```

生成物位于忽略的 `output/tmp/`；脚本从源码生成对照模块，默认基线固定为上述提交。更改源文件后请使用新的输出目录名，避免 Vite 对忽略目录保留旧模块缓存。
